# M2 — Walking skeleton (application foundation)

**Goal:** end-to-end path UI → WS → CommandExecutor → TowerSession → adapter → (mock or tower), with connection lifecycle and multi-client broadcast. Proven with a single capability (`sound.play`).
**Exit condition:** from Mac and iPad at the same time, connect, calibrate and play a sound in mock mode and on hardware. Both clients see the lifecycle.

## Files that change

```text
apps/tower-poc/src/protocols/{envelope,messages,connection,command,state}.ts (+ tests)
apps/tower-poc/src/server/
  server.ts            # HTTP static + ws upgrade
  clientHub.ts         # client registry, broadcast, clientId/label
  towerSession.ts      # owns UltimateDarkTower instance, lifecycle state machine, calibration state
  adapters/instrumented.ts (tap and event list), adapters/mockTower.ts
  commandExecutor.ts   # queue, correlation IDs, validation via inventory, timeouts, lanes, lifecycle events
  stateStore.ts        # value+origin+freshness wrapper, snapshot to db
  db/{schema.ts,client.ts,migrations/}   # better-sqlite3 + Drizzle: settings, state_snapshots
  settings.ts
apps/tower-poc/src/web/
  lib/ws.ts (socket with service-reconnect), lib/store.ts (Zustand), lib/useCommand.ts

  app/(dashboard)/page.tsx (connect/disconnect/reconnect/calibrate + play test sound)
```

## Order of work

1. Protocol messages (spec §3.2), plus a test asserting that no message can carry arbitrary bytes.
   - Result, on `feat/tower-poc-protocol-messages` (spec 1.9):
     - Client messages: `hello`, `connect`, `disconnect`, `reconnect`, `calibrate`, `command`, `restoreState`. Server messages: `welcome`, `error`, `connection`, `state`, `command.lifecycle`. The schemas are in `connection.ts`, `command.ts` and `state.ts`. The `diag.*`, `gap.*`, `verify.*`, `settings.*` and `data.clear` messages of spec §3.2 are left to the milestones that use them (M3, M4).
     - `command.params` is the one open field a client can send. `validateCommand` (in `command.ts`) checks it against the inventory and returns the schema's parsed output or the fields that are wrong; the executor (step 5) must call it before anything else touches `params`. A test walks every client message schema and fails if another open field appears.
     - Deviations from spec §3.2 as it stood, now written into it: `connection` carries `calibration`; a `command` must have an `id`.
     - The service answers a valid message it has no handler for with the error `not-implemented`. That code is temporary: steps 4, 5 and 6 replace it, and step 7 removes it. Step 4 replaced it for the four lifecycle messages, step 5 for `command`, and step 6 for `restoreState`, removing the code.
     - `welcome` is unchanged; step 7 adds the inventory and `pendingRestore`.
     - The origin check is `isAllowedOrigin` in `server.ts`; a refused upgrade gets `403`. Dev mode is the `DEV_ORIGINS` variable, which only `pnpm dev` sets (to `http://localhost:3000` and `http://127.0.0.1:3000`). If `next dev` picks another port because 3000 is taken, the UI cannot connect until that port is added. A WebSocket message over 64 KiB closes that client's connection; envelope ids are at most 64 characters.
     - Not covered by D20 as written, and not built: a site that serves its page on the service's port and then re-points its own name at the Mac's address (DNS rebinding) has an `Origin` equal to its `Host`, so it passes. Closing that means checking `Host` against the Mac's own names and addresses; it needs Bob's decision because it could lock out a name he uses.
   - Before `command` is accepted: the `/ws` origin check from spec D20, with tests for the service's own origin (accepted), the `next dev` origin in dev mode (accepted), another origin (refused) and a missing `Origin` header (accepted). The service binds `0.0.0.0`, so "its own origin" is checked against the request's `Host` header, not a fixed value.
2. `MockTowerAdapter`: scripted responses for connect, device info, calibration complete (after a delay), battery notify, and an injectable skull drop. Deterministic clock for tests.
   - From the M1 spike: the mock answers a write with a state only when the real tower did. It stays silent for the four `rotation*` sequences and for a write that changes nothing in its state (GAP-HW-010). It sends battery messages about every 2 seconds and none while calibrating (GAP-LIB-008).
   - Result, on `feat/tower-poc-mock-tower` (branched from the step 1 branch): `src/server/adapters/mockTower.ts`, `createMockTower()`. It implements the library's adapter interface, so the real library runs on top of it unchanged; two tests do exactly that (connect, calibrate, play a sound, count a skull, read the battery, and a rotation sequence timing out after 30 s).
     - Modelled on the spike: silence for the four `rotation*` sequences and for a write that changes nothing; echoes after 40 ms; a rotation reported after 1.1 s together with the duration message (the real tower sent it 1 to 2 ms earlier); the loop bit dropped from the echo; the seal sequence reported cleared 3.6 s later with its audio byte still in the state; the audio byte kept and reported in later states, no answer when it goes back to 00, and 00 in the state that ends a calibration; battery every 2 s and none while calibrating; differential readings every second; skull drops as a state with a running count.
     - Assumed, because the spike did not observe it, and marked so in the code: every non-rotation light sequence ends the way the seal one did; resetting the skull counter sends a state; a write during calibration does nothing; a sound sent twice running is echoed twice; the skull count in a packet is ignored; drum bytes that differ are a rotation even on an uncalibrated tower (the cautious reading of GAP-HW-006).
     - Calibration takes 3 s in the mock, not the real 21 s, so that mock mode is usable. All delays are options.
     - The clock is not injected. Tests use Vitest's fake timers, which is what "deterministic clock" needs; the mock uses the ordinary timer functions.
     - `cleanup()` ends disconnected without reporting a disconnect, as the real adapter's does. A packet the mock does not recognise (not 20 bytes, or an unknown one-byte command) is ignored without an error, so a malformed packet from a later step would show up as a timeout.
     - Not wired into the service yet: nothing constructs it outside tests until step 4.
3. `InstrumentedAdapter`: tx/rx/lifecycle taps that emit to a temporary in-memory event list. The full DiagnosticsBus comes in M4.
   - Result, on `feat/tower-poc-instrumented-adapter` (on top of the step 2 branch): the tap built for the spike moved from `src/server/instrumentedAdapter.ts` to `src/server/adapters/instrumented.ts`, unchanged, and gained `createAdapterEventList()`: the newest 5,000 events in memory, each with the time it was seen, and a count of what was dropped. Nothing reads the list yet; the session (step 4) owns one and the hardware smoke (step 11) reads it.
     - Not added: the service and characteristic UUIDs that spec §3.1 says each transport event carries. The adapter interface does not tell the tap which characteristic a write went to, so the tap would be repeating the library's constants, not observing anything. M4 step 4.1 already lists them and is the place to decide.
     - The spike script imports the tap from its new place; it was not run.
4. `TowerSession` state machine (spec §3.2 states). It sets `retrySendCommandMax = 0` on the tower object as soon as it is constructed, with a test (D21). Manual reconnect only (D10), and calibration resets on disconnect.
   - From the M1 spike: a test asserts that the first stateful packet after a reconnect carries no drum positions from the earlier connection (the open part of GAP-HW-006). The library's heartbeat warning is recorded and is not treated as a lost connection, and nothing reconnects because of it (GAP-LIB-008). The session knows when it asked for the disconnect, so the library's incident for it is not reported as a fault (GAP-LIB-009).
   - Result, on `feat/tower-poc-session`: `src/server/session.ts`, `createTowerSession({ createAdapter })`, with `connect`, `reconnect`, `disconnect`, `calibrate`, `status`, `subscribe`, `tower()` (for the executor) and `close`. The status is the `connection` payload as it is.
     - **Each connection gets a new adapter and a new library object**, and both are cleaned up when it ends. The library keeps the last tower state, drum positions included, in a private field that a disconnect does not clear, and builds every stateful packet from it; `isCalibrated` reads the same field. A new object is the only way through the public API to start from the default state. The GAP-HW-006 test shows both sides: within one connection a stateful packet carries the calibrated drums (`10 42`), and after a requested or an unexpected disconnect and a reconnect it carries `00 00`. `retrySendCommandMax = 0` is set on each object straight after constructing it (D21), tested while still connecting.
     - Calibration is `calibrating` from the moment it is asked for until the library's `onCalibrationComplete`. `tower.calibrate()` settles at the same point: the library's queue does not count the tower's unprompted sensor messages (differential readings) as an answer.
     - Failed connects (spec §6): tower not found → `disconnected` with `tower-not-found`; noble's "adapter not ready" → `bluetooth-unavailable`; anything else → `error` with `connect-failed`. An unexpected disconnect → `disconnected` with `unexpected-disconnect` and calibration reset; nothing reconnects. A disconnect while connecting gives the connect up. A new connect waits for the previous object's cleanup to finish, so an old cleanup cannot reach the Bluetooth stack (or the one mock tower) mid-connect; the session is already `connecting` while it waits.
     - GAP-LIB-009: a requested disconnect moves the session's connection number on before the library reports anything, so the library's `onTowerDisconnect` for it (which comes twice: once from the adapter, once from its own disconnect) is ignored and no error is shown.
     - GAP-LIB-008: the library's console logger is replaced by one that keeps only warnings and errors, as `library-warn` / `library-error` events in the adapter event list. Info messages are dropped because they name the tower's serial number. The test slows the mock's battery to every 10 s and checks the heartbeat warning is recorded and the session stays connected.
     - The server handles `connect`, `reconnect`, `disconnect` and `calibrate` (no longer `not-implemented`), sends `connection` to every client on each change, and sends the current `connection` after `welcome`. An action the state does not allow is answered with the new error code `invalid-state`, to the client that sent it only. Step 7's client hub takes over the broadcast.
     - The real tower is the default (Bob's decision, 2026-10-14). `MOCK=1` selects the mock, the switch the README and `pnpm e2e` already used; any value other than `1`, `0` or empty stops the service. There is one mock tower for the life of the service. The library loads noble when it is imported, but nothing uses Bluetooth until Connect is pressed. On SIGINT/SIGTERM the service disconnects the tower before closing.
     - Calibration limit (Bob asked for one, 2026-10-14): 30 s, which is the library's own command timeout. It applies to calibration and cannot be changed through the public API, so a longer limit is not possible, and a shorter one would end calibration in the session while the library was still waiting. Past it, `calibrate()` rejects, the library clears `performingCalibration`, and the session reports `uncalibrated` with `calibration-failed` ("did not report the end of calibration within 30 s"). Nothing is sent again. If the tower finishes later, the library no longer reports that as the end of calibration, so the session stays uncalibrated, the cautious side. The real tower took 20.6 s and 22.4 s, which leaves 7.6 s of margin. Tested with a mock that takes 60 s.
     - Not distinguished: `scanning` and `connecting`. The library's `connect` scans and connects in one call, so the session reports `connecting` for the whole of it.
5. `CommandExecutor` with lifecycle, lanes, per-capability timeouts from the inventory, and no auto-retry. It validates `params` with the inventory schema and passes the parsed output to the library, never the input; a test asserts that the library receives the schema's parsed output. `lighting.all-on` and `lighting.all-off` bypass the library's queue (`sendTowerState` goes straight to `sendTowerCommandDirect`), so the executor serialises them with the other commands. A command that arrives while `performingCalibration` is true is rejected before the library is called, with a test (D22).
   - From the step 1 review: the executor accepts only what `validateCommand` returns. Make that a type only `validateCommand` can produce, so that passing a message's raw `params` does not compile.
   - From the M1 spike: when a command's write completed and no state came back, the lifecycle ends as `indeterminate`, not `failed` or `timed-out` (GAP-HW-010). The library's own 30-second rejection for such a command is mapped to that, with a test.
   - D23: decide how to send a command the tower is known not to answer without holding the library's queue for 30 seconds, and bring the choice to Bob before building it. When it works on hardware, empty `HELD_LIGHT_SEQUENCES` and update GAP-HW-007. Until then the four `rotation*` sequences stay held.
   - Result, on `feat/tower-poc-command-executor`: `src/server/executor.ts`, `createCommandExecutor({ session, onLifecycle })`, with `submit` (validates, then runs) and `run` (takes a `ValidatedCommand`). The server sends every `command` to it and every lifecycle stage to every client; `command` no longer answers `not-implemented`.
     - **One lane for every command**, not a mechanics lane only: the library's queue does not hold `allLightsOn`, `allLightsOff` or `sendTowerState`, so only a lane above it keeps every write in order. At most 20 wait; more are rejected. A command that wrote is followed by 250 ms, the spacing the library's queue keeps. Spec §3.1 now says so.
     - `ValidatedCommand` (in `command.ts`) carries a brand only `validateCommand` can set, so the executor cannot be given raw `params`; a `@ts-expect-error` test holds it. `validateCommand` now returns `{ ok: true, command }`. The plan table in the executor is typed by `CommandableId`, so a commandable capability with no plan, or a plan for anything else, does not compile; a test checks `CommandableId` against `isCommandable`.
     - **Timeouts live in the executor's plan table, not the inventory.** They follow from how the library sends each command, which the inventory does not describe: 35 s per queued packet (the library gives up at 30 s, so it settles first), 5 s for a direct write, 1 s for a software-only one. `mechanics.rotate-with-state` with a sound is two packets.
     - Lifecycle endings and the arrival and start checks are as spec §3.1 now lists them. The parsed-output test spies on `lights` and checks it gets an equal object that is not the client's. Names become the library's numbers in the executor only (`LIGHT_EFFECT_NUMBERS`, checked against the library's `LIGHT_EFFECTS`).
     - D23 (Bob's decision, 2026-10-14, after weighing a library fork and an upstream change): `sendSilentSequence` writes the library's current state with only the sequence changed, through the public `sendTowerState`. The library's own comment in `updateTowerStateFromResponse` says a sequence left in its state re-triggers on every later packet, and only a tower report resets it, so the executor writes the state again with the sequence at 0 before its next command unless the tower has reported since. Tested on the mock: no 30 s wait, the clearing packet, no clearing after a skull drop, and a rejection on an uncalibrated tower. `HELD_LIGHT_SEQUENCES` is unchanged (it is now `SILENT_LIGHT_SEQUENCES`), so no client can send these yet; the tests build the command by hand.
     - For step 11: empty `HELD_LIGHT_SEQUENCES`, play each sequence, then send a sound, and watch whether the clearing packet cuts the sequence or the sound replays it. A silent sequence with a `soundIndex` is already rejected by the executor, because `sendTowerState` clears the audio byte; the schema could say so too when the hold lifts.
     - From the step 5 review: a silent sequence is marked for clearing before it is sent, because `sendTowerState` records it in the library's state before writing, so a send that fails or times out is still cleared before the next command. Tested, with a failed clearing write too.
     - Open from the step 5 review, not built: (a) `calibrate` does not wait for the lane, so its packet can land while a command is running and make a command the library skipped read as written. The lifecycle label would be wrong; nothing extra is sent. (b) A tower answer to a direct write that came more than 1.25 s late would resolve the next queued command in the library's queue early, showing it `confirmed`. M1 echoes came in 25 to 64 ms. Both are for Bob to weigh; step 9's executor tests are the place for either.
     - The session gained `writes()` (packets written, counted at the adapter tap) and `onTowerReport` (the library's state updates whose source is a tower response).
     - The upstream issue Bob asked for is drafted in `research/tower/upstream-issue-unanswered-commands.md`, for him to file.
6. `StateStore` plus snapshot and the restore prompt flow (D11).
   - Result, on `feat/tower-poc-state-store`: `src/server/stateStore.ts`, `createStateStore({ storage })` and `feedStateStore(session, store)`; the database in `src/server/db/` (`client.ts`, `schema.ts`, `migrations.ts`, `snapshots.ts`), with `better-sqlite3` 13.0.3 and `drizzle-orm` 0.45.3 (D17). `better-sqlite3` is added to `onlyBuiltDependencies` so pnpm builds it.
     - **One value in M2: `battery.level`** (`{ millivolts, percent }`, `device-reported`, the percentage being the library's). It starts unavailable, is `current` from the first reading, and turns `stale` when the connection ends, any way it ends. The keys are in `STATE_KEYS`, and a test checks each is an inventory property or query. Drums, glyphs, seals and skulls are left to M3 step 3.5, which shows them; see the open question below.
     - **The snapshot is the store's values that have one, saved on every change** (a battery reading is about every 2 s), as one row of `state_snapshots`. A snapshot with no values removes the row. The spec's "latest application-maintained state" is read as "the latest state the application kept": battery is not application-maintained, and D11 already says what a restored value becomes.
     - **The prompt**: on start, a saved snapshot with a value the store keeps opens it. The values are offered `stale` (they were saved before the restart, and the shutdown does not get to mark them). While it is open the saved row is not overwritten, so a restart before anyone answers offers the same state again. Yes: each value the store does not have takes the saved one as `application-maintained` and `stale` with its saved time; a value read since the start is newer and stays. No: the saved values are dropped. Either way the prompt closes and the store's own values are saved. Nothing is sent to the tower or written into the library; a test connects the mock first and counts the writes.
     - **Protocol**: `state` carries `pendingRestore{savedAt, snapshot}` while the prompt is open, so every client closes it when any one answers. The service sends `state` after `welcome` and `connection`, and to every client on each change. `restoreState` with no prompt open is `invalid-state`. `welcome` does not carry `pendingRestore` (step 7 below). Every client message now has a handler, so the `not-implemented` error code is removed here, not in step 7.
     - **Where the data lives**: `apps/tower-poc/data/tower-poc.db`, or `tower-poc.mock.db` with `MOCK=1`, so a mock run never offers its values to a real one. `DB_PATH` overrides it; `pnpm e2e` uses `:memory:`. `*.db` is already ignored by git. A database with a newer schema than the service knows is refused at start.
     - **Not built from the files list**: `settings.ts` and the `settings` table. No M2 step reads a setting; the step that first does adds them as a new migration. The migrations are one module (`db/migrations.ts`, SQL run in order, counted in SQLite's `user_version`), not a folder of drizzle-kit output, so there is no generator to add.
     - Open, for Bob (M3 step 3.5): the session gives each connection a new library object (step 4), so the library's broken seals and skull count start from nothing on every connect. Shown from the library, a reconnect would make every broken seal look restored. The store will have to own the seals the person marks, as `application-maintained`, rather than read them from the library.
7. `ClientHub` broadcast. `welcome` carries versions and inventory. (`pendingRestore` travels in `state` since step 6, which follows `welcome`.)
   - Result, on `feat/tower-poc-client-hub`: `src/server/clientHub.ts`, `createClientHub()`. It registers each `/ws` socket under a new client id when it connects and forgets it when it closes, keeps the label from `hello`, and is the one broadcast: `connection`, `state` and `command.lifecycle` all go through it, serialised once per message. The server exposes it as `hub`; nothing reads the client list yet (M4's export lists the clients).
     - `welcome` now carries `versions.library` and `versions.data`, read from the installed packages' own manifests (`versions.ts`), and `inventory`: every entry in inventory order as `src/protocols/inventoryWire.ts` defines it. That is the entry without its `params` schema, which is code and cannot travel as JSON, plus `commandable` (`isCommandable`). The web keeps validating with the schemas compiled into it from the same package. About 24 KB, once per connection.
     - `verificationOverlay` and `settings` from spec §3.2 are not in `welcome` yet: there are no verifications (M4) or settings (no M2 step reads one) to send.
     - A message is still accepted before `hello`; the client then has an id but no label. Requiring `hello` first would change the protocol for no gain in M2.
8. Web: socket client, store, header (tower, calibration, service and mock states), and Dashboard controls.
   - Result, on `feat/tower-poc-dashboard`: `src/web/lib/ws.ts` (the socket), `lib/service.ts` (the view and the pure reducers), `lib/store.ts` (Zustand 5.0.15), `lib/useCommand.ts`, `lib/labels.ts`; components `ServiceConnection`, `ConnectionHeader`, `MockBanner`, `RestorePrompt` and `Dashboard`. The web part gains Vitest (5.0.4, as the other parts) for the pure modules. The plan's `app/(dashboard)/page.tsx` is `app/page.tsx`, the page that already existed.
     - **The socket** sends `hello` on every open and reconnects to the service by itself (0.5, 1, 2, then every 5 s), because that is a network link, not a physical action. It reports `reconnecting-to-service`, then `service-unreachable` after three failures in a row. It never queues or re-sends: a message sent while the link is down is refused, the page says "Not sent", and the person presses again. Message ids are made without `crypto.randomUUID`, which an iPad on the LAN over plain http does not have. Messages that fail the protocol schema are dropped with a console warning.
     - **Unknown stays unknown**: when the link to the service drops, the view forgets the tower's connection, its state and `welcome`, so the header shows "Unknown" until the service sends them again. The store replaces its state on each update rather than merging, which is what makes the forgetting work; a drive across a service restart caught the merge.
     - **The header** shows tower, calibration, service link and battery (with ", stale" when it is not current, "Unavailable" when the service has none); the mock banner shows when `welcome.tower` is `mock`.
     - **The Dashboard**: Connect (Reconnect instead after an `unexpected-disconnect`, D10), Disconnect, Calibrate, device information, the tower's error with what to do about it, the restore prompt, and "Play test sound" (sound 1). Each button is enabled only in the states the service accepts; the service still decides. Play is disabled while calibrating (D22) and locked while its own command is under way. The panel shows the newest test-sound lifecycle from any device, saying which, so every screen shows the same one (D7). A refused action shows the service's message.
     - **Protocol**: `welcome` carries `tower: "mock" | "bluetooth"` (spec 1.15), so the page can say which tower it drives.
     - From the step 8 review: the service does not replay lifecycles, so a command that had not ended when the link dropped may never get its end. The view marks such commands interrupted. That releases the control's lock, and the panel says "Outcome unknown: the link to the service dropped before it ended" instead of showing an unfinished lifecycle as live. A command counts from the moment it is sent, before any stage arrives. The view keeps every client id the service has given the page (each socket gets a new one), so "from this device" survives a reconnect. The socket counts a link as working only after `welcome`, so a service that accepts and drops every socket is reported unreachable.
     - Checked by hand with Playwright against `pnpm start` on the mock: an iPad window and a desktop window, connect from one, calibrate from the other, play from the iPad, both show `Queued → Started → Sent → Confirmed`. And at phone width: a service restart with the page open shows "Reconnecting" with the tower unknown, then the restore prompt; Restore shows the battery stale. No console errors, no sideways scroll. Step 10 makes the first of these an e2e test.
