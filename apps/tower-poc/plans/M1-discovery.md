**Status:** approved by Bob, 2026-10-13. Step 1 is built on `feat/tower-poc-pin-versions`, step 2 on `docs/tower-poc-api-surface`, and steps 3 and 4 together on `feat/tower-poc-inventory`. ## Order of work

1. Pin versions. Record the library's `package.json` version plus the `ultimatedarktowerdata` version and sound catalog count.
   - Result: `ultimatedarktower@7.1.2`, `ultimatedarktowerdata@3.0.0` and `@stoprocent/noble@2.8.0`, all exact, in `tower-poc-server`. The library declares `ultimatedarktowerdata: ^3.0.0` and a peer `@stoprocent/noble: ^2.0.0`; 3.0.0 and 2.8.0 were the latest of each on 2026-10-13. `TOWER_AUDIO_LIBRARY` has 113 entries.
   - The lockfile also re-keys the Vite and Vitest entries with `(yaml@2.9.1)`: `yaml` arrives with noble's dependencies and satisfies Vite's optional peer. Build and e2e pass with it.
   - pnpm did not run the install scripts of `@stoprocent/noble`, `@stoprocent/bluetooth-hci-socket`, `usb` and `@serialport/bindings-cpp`, and none is approved. noble ships a prebuilt `darwin-x64+arm64` binary, so macOS needs no build; the other three serve Linux and Windows. Whether noble loads and sees the tower is the step 5 spike.
   - The npm package holds only `README.md` and `CHANGELOG.md`. `API_REFERENCE.md`, `BLE_DIAGNOSTICS.md` and `TOWER_TECH_NOTES.md` for step 2 have to come from the library's source repo.
2. Read the library's `API_REFERENCE.md`, `BLE_DIAGNOSTICS.md` and `TOWER_TECH_NOTES.md`, and diff them against the public surface listed in spec §4.
   - Result: `research/tower/api-surface-7.1.2.md`. The documents were read from the library's repo at tag `ultimatedarktower@7.1.2`; `API_REFERENCE.md` is only an index there, so the `api/` pages it points to were read instead. `BLE_DIAGNOSTICS.md` and the packet layout in `TOWER_TECH_NOTES.md` were read by heading only and are left for step 7.
   - Five methods and about twenty properties are not in the spec §4 table. The spec changes are listed in the note and are made with the inventory in step 3.
   - Two findings needed Bob's decision before M2: the library retries a failed command write up to five times by default, and a command sent during calibration is dropped but still resolves. He decided both on 2026-10-13: spec D21 and D22, with the work in M2 steps 4 and 5.
3. Write `inventory.ts` (Zod param schemas from the library's types: `TowerSide`, `TowerLevels`, `SealIdentifier`, `Lights`, `LIGHT_EFFECTS`, sound index range).
   - Result: 52 entries (22 commands, 3 lifecycle actions, 13 queries, 7 events, 7 properties) and 17 exclusions (3 raw senders, 6 service-internal, 6 logging, 2 helpers). After the spike holds (spec 1.6; now 38 and 7, see step 8) 37 entries were `available`, 8 `requires-calibration`, 4 `not-exposed` and 3 `unsupported`, and 15 are commandable. As first built, 38 entries were `available`, 8 `requires-calibration`, 3 `not-exposed` (the monitoring settings) and 3 `unsupported` (`doorReset`, `unjamDrums`, `overwriteDrumStates`).
   - `inventory.ts` does not import the library, so the values it repeats (sides, levels, corners, the six effects, layer and volume counts) are written out and compared with the library in the coverage test. Catalog ranges come from `ultimatedarktowerdata@3.0.0`, now an exact dependency of `tower-poc-protocols`.
   - As first built, the schemas were stricter than the library in four places (two more were added in review, below): the `a`/`b` base-light aliases are not offered, `randomRotateLevels` needs its level, a `lights` command must name at least one light and each light once, and an out-of-range volume is rejected where the library clamps it.
   - Review changes (spec 1.5): `seals.break` lost its `volume` (the library discards it, so the schema is stricter than the library there: the fifth place) and `mechanics.random-rotate` takes a named `drums` enum instead of `level` 0 to 6 (the sixth; `RANDOM_ROTATE_DRUMS` maps names to the library's numbers).
   - Done: `pnpm inventory:doc` (in `apps/tower-poc/`) writes `docs/capabilities.md` from the inventory with `src/protocols/generateCapabilitiesDoc.ts`, run by `tsx` (`tower-poc-protocols` gained `tsx` 4.23.15 and `@types/node` 22.20.5 as exact devDependencies, the versions the server uses). `capabilitiesDoc.test.ts` fails when the committed file is out of date.
   - The millisecond bounds on the three monitoring settings are ours; the library documents none. Those entries are `not-exposed`, so nothing uses the bounds yet.
4. Coverage test: enumerate `Object.getOwnPropertyNames(UltimateDarkTower.prototype)` plus instance callbacks, and fail on any that are unmapped and not excluded.
   - Result: `apps/tower-poc/src/server/inventoryCoverage.test.ts`. It is in the server package because the library is installed there and `tower-poc-protocols` must not depend on it. The inventory's own tests stay in `protocols/inventory.test.ts`.
   - The public surface is read from `UltimateDarkTower.d.ts`, which marks the private members, and then compared in both directions with the prototype and an instance. It is 73 members: 46 methods, 7 callbacks, 16 accessors and 4 fields. The step 2 note says 53 methods; 46 is the count from the type file.
   - Importing the library and constructing it with `BluetoothPlatform.NONE` does not load `@stoprocent/noble`: the only `require` of it is in the Node adapter, which the factory loads for the `NODE` platform only. The test also blocks `process.dlopen` while the library is in use and asserts that it was never called.
   - Steps 3 and 4 share one branch, against the rule of one branch per step, because the test belongs with the code it tests.
5. **Hardware spike, run by Bob on the Mac with the tower nearby.** `pnpm -F tower-poc-server spike` runs these steps through `InstrumentedAdapter(NodeBluetoothAdapter)`:
   1. connect
   2. read device info
   3. calibrate
   4. playSound(1)
   5. allLightsOn / allLightsOff
   6. a single rotate
   7. watch battery and skull notifications for 60 seconds
   8. disconnect

   It dumps every tx/rx packet as hex to `spike-<ts>.jsonl`.
   - Built on `feat/tower-poc-spike`: `scripts/spike.ts` (entry), `scripts/spikeSteps.ts` (the steps and the runner, with no Bluetooth code, tested against a fake tower) and `instrumentedAdapter.ts` (the tap; M2 step 3 builds on it). The order differs from the list above because step 6 has to come before calibration: connect, device info, lights, sound and `breakSeal` before calibration, calibrate, sound, lights, `rotateWithState`, legacy `Rotate`, `randomRotateLevels` (top drum only), a looped sound, the 60-second watch, the four rotation sequences, disconnect. (Runs 1 and 2 had the sequences straight after lights; they moved to the end after run 2.)
   - How it keeps to the safety rules: it refuses to start without a terminal; Bluetooth is loaded only after `YES` is typed; every step is described and needs `r` to run, and can be skipped; nothing is retried (`retrySendCommandMax` is set to 0 first, D21); the three drum moves are skipped unless the tower reports calibrated; a step is skipped while the tower is calibrating, because the library would drop it and report success (D22); it always disconnects at the end, also on quit, error or Ctrl-C.
   - A step that times out ends the run, except the rotation-sequence step since run 2 (below). The library holds a written command for 30 seconds waiting for a response and sends nothing else meanwhile, so with a shorter limit a command confirmed earlier could reach the tower later, after the script had moved on. For a queued command the library's 30 seconds always fires before the script's 35; the script treats that rejection ("Command timeout after …") as a timeout too and ends the run. The 35 seconds is what applies to `allLightsOn` and `allLightsOff`, which bypass the queue. Calibration has a further 120-second wait for the tower to finish. Disconnecting clears the library's queue. Found in the two safety reviews before the first run.
   - The rotate commands set all three drums to absolute sides. The rotate steps read where the library has tracked the middle and bottom drums and send those back, so only the top drum is asked to move, and the warnings say the other two may turn if that tracking is wrong. The legacy step never targets east, because the library's legacy code for top-east lacks the calibrated bit.
   - Notes for Bob when running it: calibrate in the same run before any drum step. If a step prints `timed-out`, the tower may still carry the command out; wait until it is still. Two things only the tower can answer: whether it reports state when calibration ends (if not, the calibrate step waits out its limit and the run ends before the drum steps), and whether the state after `rotateWithState` shows the new position.
   - For the write-up: `calibrated` in each `step-start` record is what the tower had reported so far. A tower may calibrate itself when switched on, so read that flag on the lights, sound and seal steps before concluding anything about GAP-HW-001 or GAP-HW-006. If it says `true`, those steps did not test an uncalibrated tower.
   - Output: `research/tower/spikes/spike-<time>.jsonl` holds every packet as hex, each step's result and what Bob typed about what he saw. The serial number and system id are recorded only as present. The library's own diagnostics export goes to `spike-<time>.diagnostics.local.json`, which git ignores because it names the tower.
   - Runs 1 and 2 (2026-10-13; this bullet is the state after run 2, and run 3 below covers what it lists as not yet run), written up in `research/tower/spikes/2026-10-13-noble-macos.md`: noble connects on macOS once Bluetooth permission is granted; lights, sound and the seal sequence work on an uncalibrated tower with no drum motion; calibration takes about 20 seconds and the tower reports state when it ends. The run ended at the first rotation sequence, which the tower played but did not answer, so the library timed out after 30 seconds. Not yet run: the three rotate steps, the looped sound, the 60-second watch and the other three sequences.
   - After run 2 the rotation-sequence step was moved to the end and, for that step only, the library's 30-second rejection is recorded as "the tower did not answer" and the next sequence is tried.
   - Run 3 (2026-10-13) ran every step run 2 had not reached; Bob skipped the four that run 2 covered. Calibration took 22.4 seconds. All three rotates moved only the top drum and the tower's state showed the new position about 1.1 seconds after each; `rotateWithState` kept the lights, legacy `Rotate` and `randomRotateLevels` sent zero light bytes and the lights went off. Bob answered that the sound sent with the loop bit did not loop; the tower's echo did not carry the bit. Two skull drops arrived as state messages with a running count. All four rotation sequences played lights, moved no drum, and got no answer from the tower.
6. Also in the spike: test whether lights and sounds work **before** calibration (GAP-HW-001).
   - Watch for drum motion, not only for whether they work: every stateful command packs the library's tracked drum bytes, which before calibration are north/north/north with `calibrated: false`.
   - Check whether the four `rotation*` light sequences (`rotationAllDrums`, `rotationDrumTop`, `rotationDrumMiddle`, `rotationDrumBottom`) move anything or are light animations only.
   - Questions the spike must answer to lift the holds (each hold is temporary; the entry's `evidence` says so):
     - GAP-HW-006, `seals.break` (held as `requires-calibration`): send it before calibration and watch for drum motion or an error. If nothing moves, make it `available` again.
     - The reason for holding `seals.break` is that every stateful command carries the library's drum positions. That is equally true of `lighting.set`, `lighting.set-led`, `lighting.all-on`, `lighting.sequence` and `sound.play-stateful`, which stay available before calibration (D9). Whatever the spike shows about drum motion before calibration applies to all of them, not only `seals.break`: if anything moves, D9 changes.
     - GAP-HW-007, `lighting.sequence` (the four `rotation*` names are in `HELD_LIGHT_SEQUENCES`): play each and watch the drums. If none moves, empty the list.
     - GAP-HW-008, `sound.play-stateful` (no `loop`): find out whether a looped sound can be stopped, by any command or by disconnecting. If it can, add `loop` back.
     - GAP-HW-009, `mechanics.rotate` (legacy, `not-exposed`): send it once after calibration and look at the lights; confirm they go off, and that `rotate-with-state` keeps them. Also confirm the same for `random-rotate`.
   - Answers (runs 2 and 3; the write-up has the evidence and its limits). The inventory, gap seed and spec are not changed yet; that is step 8.
     - GAP-HW-001 and D9: lights and sound work before calibration and nothing moves. D9 stands.
     - GAP-HW-006: `seals.break` worked before calibration and nothing moved. The hold can be lifted.
     - GAP-HW-007: none of the four sequences moves a drum. The tower answers none of them, so the library reports each as failed after its 30-second wait (the 30 seconds is from run 2's error text and the library's code). Bob decided on 2026-10-13 to keep them held until M2.
     - GAP-HW-008: the one sound tried did not loop, so whether a loop can be stopped was not tested. `loop` stays out.
     - GAP-HW-009: confirmed. Legacy rotate turns the lights off and `rotate-with-state` keeps them. `random-rotate` turns them off too.
7. Write the observability assessment. It covers what we get from the adapter tap compared with the library recorder, and whether responses can be correlated to commands.
   - Result: `research/tower/observability.md`, on `docs/tower-poc-observability` (branched from `feat/tower-poc-spike`, which holds the logs it reads). The adapter tap sees every byte and no identifiers. The library's recorder, as the spike ran it, holds no bytes and only its last 450 to 500 events, but names the library call behind each packet and records timeouts and heartbeat warnings. The two clocks agree to the millisecond. A response matches a command when the tower echoes it (9 of 16 writes in run 3, plus calibration); six writes got no answer and the tower never names the command, so GAP-DIAG-001 stays open with a narrower description.
   - Three things for M2 came out of it: the recorder has to be ingested as events arrive, not exported at the end; the library's heartbeat check expects a battery message every 200 ms where this tower sends one about every 2.0 s and none during calibration; and a normal disconnect is recorded as an incident.
   - Not run: the recorder's `capturePayloads` option and its `onEvent` sink. `BLE_DIAGNOSTICS.md` was not read; the assessment rests on the installed code and the three exports.

     - The M2 plan (steps 2, 4 and 5) and the M4 plan (step 4.1) carry the work these lead to.

- Calibration requirement turns out to be global, which changes D9.
