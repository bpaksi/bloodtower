# M3 — Functional coverage (Lights, Sounds, Mechanics, Tower State, Verify)

**Goal:** every inventory entry with `availability ≠ unavailable` has a UI control on its page. Every entry has `mock-tested` status, and the Verify mode records hardware results to SQLite.
**Exit condition:** coverage test plus "UI mapping" test green. Bob has run the Verify pass on hardware for each page.

Use the `tower-capability` skill for every control: inventory → protocol → executor → UI → test → gap.

## Steps (one branch each)

| Step | Branch | Scope |
|---|---|---|
| 3.1 | `feat/tower-poc-controls-framework` | Inventory-driven form generator from Zod params, pending lock, requested-vs-confirmed display, disabled-when-disconnected or uncalibrated rules |
| 3.2 | `feat/tower-poc-lights` | Doorway (side×level), ledge (corner), base, effects, all on/off, light overrides |
| 3.3 | `feat/tower-poc-sounds` | Catalog from `ultimatedarktowerdata` (ID plus name, numeric fallback), filter, play |
| 3.4 | `feat/tower-poc-mechanics` | Rotate per drum, rotate-with-state, random rotate (confirmation dialog), calibrate. Mechanics lane serialized. No stop control. |
| 3.5 | `feat/tower-poc-tower-state` | Drums, glyphs, seals (break/mark/restore/reset), skulls (count/reset), battery history chart. Origin, freshness and timestamp shown on every value. |
| 3.6 | `feat/tower-poc-verify-mode` | `verifications` table, Verify toggle on control pages, result form, runtime overlay into inventory, capability summary on Dashboard. The hardware pass is in short chunks (see below). |

**The Verify pass comes in short chunks** (Bob, 2026-10-14): not one long session on the tower, so that nothing is recorded wrongly. Each chunk is small and stands alone, for example one page or one group of capabilities, and its results are saved when it ends, so a pass can stop and resume between chunks. A long run is used only where length is what is being tested.

Branch names follow the repo convention, `feat/tower-poc-<slug>`; this table first had them without the app.

## Results

### 3.1 Controls framework (`feat/tower-poc-controls-framework`)

- **Form generator**: `describeParams` and `buildParams` in `src/protocols/paramFields.ts`. It reads a capability's Zod `params` and gives one field per value: enums, bounded integers and booleans, also inside a nested object (a seal's side and level), each with a label from its name and whether it may be left out. Anything else is refused with a reason, not guessed at; of the commandable capabilities only `lighting.set` (its light lists) is refused, and a test holds that list, so 3.2 gives it its own component as the risks below already said. A form filled with each field's first allowed value passes `validateCommand` for every other commandable capability (tested). It lives in the protocols package because that is where Zod and the schemas are.
- **The form never decides what is valid**: the page builds `params` from what was entered and checks it with `validateCommand`, the service's own check, before sending; the form sets `noValidate` so the schema's message is the one shown. An empty optional field is left out (the library's default applies), an empty required one is left out and named by validation, and text that is not a whole number is passed on as text for validation to name. No enum is preselected for the person. A rejection from the service with field issues is shown on the fields the same way. From the review: an issue is never dropped. One on a nested object no field stands for (a seal left wholly empty is reported at `seal`) goes on each field inside it, and one that matches no field is shown for the whole form (`errorsByField`, tested). The service's field errors clear once the person edits.
- **Disabled rules**: `controlState` in `src/web/lib/controls.ts`, in the executor's order: service unreachable, not offered by this service (from `welcome`'s inventory, so the service's truth wins), tower not connected, calibrating (D22), not calibrated for a `requires-calibration` capability (D9). Each says why next to the button.
- **Pending lock**: `useCommand` as in M2: one command per control until it ends or the link drops.
- **Requested vs outcome**: `CommandStatus` shows the newest command for the capability from any device (D7), with "Requested" and "Outcome" apart. Only `confirmed` reads as the tower having answered; `indeterminate` reads "Sent, no answer" (GAP-HW-010), and an interrupted command reads "Outcome unknown". The values requested are shown only on the device that sent them: `command.lifecycle` does not carry params, and adding them was not needed for this step.
- **`CapabilityControl`** puts these together for one capability. The Dashboard's test sound is now one (`sound.play`, sound 1 by default, with a sound field), which is how this step is proven end to end; the control pages are left to 3.2 to 3.5. The two-clients e2e test gained the disabled reasons, a refused out-of-range value with nothing sent, and requested vs outcome on both devices.
- **Docs, from Bob's decisions of 2026-10-14**: spec §3.2 now has verifications and `verificationOverlay` in step 3.6, not M4. GAP-LIB-010 records that a late tower answer can confirm the next queued command; nothing is built for it, and if the Verify pass shows a `confirmed` the tower did not earn, it is fixed with the bugfix skill.

### 3.2 Lights (`feat/tower-poc-lights`)

- **Inventory, protocol, executor**: nothing new. The five lighting commands were already in the inventory with their schemas, and the executor already mapped each to the library (M2). No new message type or state field.
- **Lights page**: all on (optional effect), all off, set lights, light sequence (optional sound) and set one LED. Four are `CapabilityControl`s. The descriptions say what the form cannot: the rotation sequences need a calibrated tower and no sound and end as "Sent, no answer" (D23), `rotationDrumMiddle` is not offered (GAP-HW-007), and what the LED layer numbers mean.
- **`LightsControl`** for `lighting.set`, the one schema the generated form refuses: one choice per light (12 doorway by level and side, 4 ledge, 8 base), each "Leave as is" or one of the six effects. Only chosen lights are sent. Nothing chosen is refused by the service's validation ("Name at least one light."), shown on the page, with nothing sent. The params and the requested text come from `src/web/lib/lightsForm.ts`, which is pure and tested. Requested is read from the parsed params that were sent. The control has the same disabled rules, pending lock and status as `CapabilityControl`. Both now read these through `src/web/lib/useControl.ts`.
- **Requested vs confirmed**: as in 3.1, each control shows what was requested and the command's outcome. The lights the tower reports (`state.current`) are not shown here; that value is published from step 3.5.
- **Tests**: executor test "lighting on the mock" sends each lighting command to a connected tower and to a calibrated one. Each writes a packet and the mock answers. A rotation sequence is refused before calibration with nothing written, and after it ends as `indeterminate`. The e2e test `tests/tower/lights.spec.ts` runs on the iPad first. It uses every control before connecting (each shows why it is disabled) and after (each sends and shows requested vs outcome). It covers the refused empty light set and the refused rotation sequence, and takes screenshots at the three viewports with no sideways scroll. The five lighting entries are `mock-tested`. The inventory test now lists which ids may claim that and the test backing each.
- **E2E layout**: the tests that drive the shared mock tower moved to `tests/tower/` and run in their own Playwright project, `tower`, with one worker. Each expects to find the tower disconnected, so two of them must not run at once. `two-clients.spec.ts` moved there and lost its desktop-only skip.
- **On the tower**: these commands change lights only; nothing moves. Bob checks them in the Verify pass (3.6).

### 3.3 Sounds (`feat/tower-poc-sounds`)

- **Inventory, protocol, executor**: nothing new. `sound.play` and `sound.play-stateful` were already in the inventory with their schemas and mapped by the executor (M2). No new message type or state field.
- **Catalog**: `SOUND_CATALOG` in `src/protocols/soundCatalog.ts`, read from `TOWER_AUDIO_LIBRARY` in `ultimatedarktowerdata` like the inventory's sound range: one entry per index the schema accepts (113), with its name and category. An index the data does not name, or names with an empty string, is listed as "Sound <n>" (the numeric fallback, tested with made-up data). It is in the protocols package because that package already depends on the data and is bundled into the UI.
- **Sounds page**: `SoundCatalog` lists every sound with a play button for `sound.play`. The filter matches a whole number to that index exactly and to names containing the digits, and otherwise names and categories, ignoring case (`src/web/lib/soundFilter.ts`, pure and tested). A category select was added beyond the plan, as the data has categories and it makes 113 rows easier to scan on the iPad. One `sound.play` command at a time from the catalog: while one is under way every play button is disabled and the pressed one reads "Playing…". The lock lasts until the command ends, normally when the tower answers as the sound starts, not until the sound ends (GAP-LIB-007). The volume control has its own lock, so one play from each can be under way together; the executor's lane still runs them one after the other. Requested names the sound ("12 Letha"), apart from the outcome, with the same disabled rules as `CapabilityControl`.
- **Play with volume**: `sound.play-stateful` is a generated `CapabilityControl` on the same page (sound number and optional volume 0 to 3). The description says what the levels do on the tower is not known (GAP-HW-003) and that there is no loop (GAP-HW-008).
- **Tests**: executor test "sound on the mock" plays sounds 1 and 113 and the volume form with no volume and each of 0 to 3, on a connected and on a calibrated tower; each writes and is confirmed. A sound outside 1..113 is rejected with nothing written. The e2e test `tests/tower/sounds.spec.ts` runs on the iPad first: the catalog of 113 before connecting (each button disabled, with why), filtering by number, name, category and to nothing, then two sounds played from the catalog, a refused out-of-range volume play with nothing sent, and one played with a volume; screenshots at the three viewports with no sideways scroll. Both sound entries are `mock-tested`.
- **On the tower**: sounds only; nothing moves. Bob checks them in the Verify pass (3.6).

### 3.4 Mechanics (`feat/tower-poc-mechanics`)

- **Inventory, protocol, executor**: no change to the inventory schemas. One optional field on `command.lifecycle`, `written: false` (below). The three rotations were mapped in M2, and every command already shares one lane, so mechanics are serialized with everything else (spec §3.1). `mechanics.rotate` stays not offered (GAP-HW-009).
- **Mechanics page**: Calibration (the Dashboard's action, never automatic, refused by the service while a command is waiting or running), Rotate drums (`rotate-with-state`, a side per drum and an optional sound), Rotate one drum (`rotate-drum`) and Rotate drums at random (`random-rotate`). No stop control, and the page says the tower has none. Each control locks until its command ends, and every rotation is disabled until the tower is calibrated (D9).
- **Named choices**: `rotate-drum` takes numbers; `CapabilityControl` now takes `choices`, names for an integer field's values (`applyChoices` in `src/web/lib/controls.ts`), so the person picks "bottom" and "north" and the number is sent. The requested text uses the names. A name list that does not fit the field's range throws (tested).
- **Confirmation**: `CapabilityControl` takes `confirm`. A valid command waits in an in-page alert dialog that repeats what will be sent, with Cancel focused; Cancel or Escape sends nothing. The dialog is withdrawn as soon as the control cannot be used (tower dropped, calibration lost, service gone), so it cannot be confirmed later against a tower someone else reconnected (from the review). Random rotate uses it and says that the drums cannot be stopped and every light goes off (GAP-HW-009). Seal break in 3.5 can use the same.
- **"Not sent"**: a rotation to where the drums already are is not written by the library, and the executor ends it `indeterminate` with that reason (M2). The page used to read "Sent, no answer" for it. The executor now marks that ending `written: false` on `command.lifecycle` (spec 1.19, §3.2), and `stageName` names it "Not sent" in the outcome and the lifecycle (tested). The field is explicit because a page that joined late, or lost its link for a moment, may not have seen the stages before it; the first version guessed from a missing `write-completed`, which the review showed could call a rotation that happened "Not sent".
- **Random rotate on the mock**: the library picks the sides. If no drum moves, the library still sends the packet and the mock does not answer, so it ends as "Sent, no answer" after 30 s (GAP-HW-010); the description says so. What the tower does then is for the Verify pass.
- **`lib/towerActions.ts`**: the Dashboard's rule for which of Connect, Reconnect, Disconnect and Calibrate is allowed, moved out so the Mechanics page uses the same one (tested).
- **Not here**: `mechanics.drum-position` and `mechanics.long-command-in-progress` are values, not controls; the state store publishes them from step 3.5, which shows them on this page too.
- **Tests**: executor test "mechanics on the mock": each rotation on a calibrated tower is written and confirmed; random rotate for every set of drums, with `Math.random` fixed so a drum moves; a rotation to the current sides writes nothing and says so; every rotation is refused before calibration with nothing written. The e2e test `tests/tower/mechanics.spec.ts` runs on the iPad first: every control disabled with its reason before connecting and before calibrating, calibrate from this page, the two rotations by name, the repeat that is not sent, the random rotate cancelled with Cancel and with Escape (nothing sent) and then confirmed, a confirmation left open withdrawn when another device disconnects the tower, no stop control, and screenshots at the three viewports and of the confirmation. The three rotations are `mock-tested`.
- **On the tower**: these move the drums. Calibrate first; Rotate drums and Rotate one drum keep the lights; random rotate turns them off. Nothing can stop a rotation once sent.

### 3.5 Tower State (`feat/tower-poc-tower-state`)

- **Bob's decisions** (2026-10-14, spec D24): seals and skulls are the app's own record, `application-maintained`, saved in SQLite; a reconnect changes nothing, Reset is explicit, the library's record is ignored and not seeded. Asked at the start of this step: the record loads at start with no prompt (the D11 prompt keeps covering readings), Mark broken, Mark restored and Clear all work with no tower, and the app's skull count has its own reset apart from the tower's counter.
- **Inventory**: `serviceOnly` marks a command that changes only the service's record (`seals.mark-broken`, `seals.mark-restored`, `seals.reset` and the new `skulls.reset-record`, which maps no library member). It travels in `welcome`, so the page enables those controls with no tower. `seals.random-unbroken` is now `not-exposed`: it reads the library's record, which the service does not keep. `skulls.reset-count` is retitled "Reset the tower's skull counter". The six seal and skull commands are `mock-tested`.
- **Found while building**: at 7.1.2 `resetTowerSkullCount` does not send the firmware's `resetCounter`; it queues a state packet with the skull counter at 0, and on the mock it ends "Sent, no answer" (GAP-LIB-012, for the Verify pass). The library's `onSkullDrop` fires on the first report of every connection with the tower's whole count, so the app counts rises from that first report on (GAP-LIB-011).
- **Protocol**: `towerValues.ts` gives each stored value a schema (battery reading and history, drum positions, glyph positions, broken seals in level then side order, skull count with its start time). The store checks a value against it before storing it and the page reads values with it, so a value off its schema is shown as unavailable. No new message type.
- **Store and database**: readings and the record are kept apart in `stateStore.ts`. The record is saved in a new `app_records` table (migration 2, `db/records.ts`), saved fresh at once on a first run so the skull count's start time lasts, started afresh with a warning if a saved row cannot be used, never made stale, and left out of the snapshot. `towerRecords.ts` changes it: seals kept once each in order, a skull drop added, the two resets.
- **Feed**: drums and glyphs from the library while the tower is calibrated, refreshed on each tower report, on calibration, and as each command ends (the library moves its glyphs after a rotation with no report after it); stale on a disconnect or a new calibration. The battery history keeps one reading per 30 s, at most 240, carried on across connections and through a restore.
- **Executor**: service-only commands run with no tower checks and change the record; `seals.break` adds its seal to the record only once the tower has confirmed it. The service's commands still go through the one lane, so they wait behind a running command.
- **Tower State page**: the seal grid (level by side), the four seal controls (Break and Clear all ask first, as random rotate does), the skull count with "Since" and its two resets (Reset count asks first), drum positions, glyphs by side, and the battery with its history chart (one line, crosshair and reading on hover or touch, a table view). Every value shows origin, freshness and time through `ValueMeta`, and unavailable with the reason. The Mechanics page also shows the drum positions.
- **Not here**: `mechanics.long-command-in-progress` is not published. The library clears it on a timer, not on a tower signal, so it would need polling, and the lane's own lock already shows a running command.
- **Tests**: executor "seals and skulls" (the record with the tower disconnected, connected and calibrated, nothing written; a confirmed break recorded and an unconfirmed one not; the tower counter packet); state store record tests (first run, load with no prompt, unusable row, never stale, not in the snapshot, failing save); the feed's battery history, drums and glyphs, and skull counting across a reconnect; `db/records.test.ts` across a restart; web `towerState.test.ts` and the service-only rule in `controls.test.ts`. The e2e test `tests/tower/state.spec.ts` runs on the iPad first: the record before connecting, a reload, readings unavailable then current, the break cancelled and confirmed, the tower counter, the record unchanged and the readings stale after a disconnect, and screenshots at the three viewports with no sideways scroll.
- **On the tower**: Break a seal plays the seal lights and sound; no drum moves. Reset tower counter writes a state packet; what the tower does with it is for the Verify pass. Nothing else on the page reaches the tower.

### 3.6 Verify mode (`feat/tower-poc-verify-mode`)

- **Protocol**: `verify.record{capabilityId, result, notes}` (client, with an `id`) and `verify.changed{verificationOverlay}` (to every client, correlated to the recording `id`); `welcome` gains `verificationOverlay` (`src/protocols/verification.ts`). A `partial` or `fail` needs notes, which is what its gap entry is written from. `sessionId` is left out until saved diagnostics sessions exist (M4); the column is there and null. The raw-bytes guard test now lists the two new text fields; neither reaches the tower.
- **Database**: migration 3 adds `verifications`, rows only added (`db/verifications.ts`). A row that cannot be read is skipped with a warning. `environment` is `{tower, client}`: which tower the service drove and the device's label.
- **Overlay** (`src/server/verifications.ts`): the newest result per capability for the tower the service drives now, so a mock result never shows on the real tower nor hides a real one (the mock already has its own database; this also holds if one is shared). `effectiveVerification` reads `hardware-verified`, `hardware-partial` or `hardware-failed` only from a `bluetooth` result; the inventory never claims them (D14). Only capabilities with a `uiLocation` can be recorded.
- **UI**: a Verify mode toggle on the Dashboard, Lights, Sounds, Mechanics and Tower State pages, kept per device in the browser. On, the page shows its checklist (`VerifyPanel`): the page's capabilities split by category into closed groups, each with "n of m recorded", every row with its status, newest result (result, time, device, library version, notes) and a Pass/Partial/Fail form. One checklist per page rather than a form inside each control, because most rows (events, properties, queries) have no control of their own. On the mock it says results never count as hardware-verified.
- **Dashboard**: the capability summary, counts by availability and by verification, and "Verify pass: n of m capabilities on the control pages" recorded. The Diagnostics page's three entries wait for that page (M4).
- **Tests**: protocol (`verification.test.ts`, `messages.test.ts`), server (`verifications.test.ts`: newest per capability across a restart, the other tower's results, refusals, unreadable rows; `server.test.ts` "Verify mode (D14)": broadcast to every client, `welcome` for a late client, refusals to the sender only, a failed save), web (`verify.test.ts`, `service.test.ts`). The e2e test `tests/tower/verify.spec.ts` runs on the iPad first with a Mac beside it: off by default, a fail refused without notes, saved with notes, seen on the Mac, a pass from the Mac seen on the iPad, kept across a reload, a checklist on every control page, the Dashboard count, and screenshots at the three viewports with no sideways scroll.

- **From the review**: a refused record is read by its own id (`refusals` in the view), so a later error to the page cannot put the row back to "Recording…" (blocking, fixed and tested). The rows stay through a moment without the service, keeping what was typed, with the last result shown as unavailable, and a record sent on a socket that has since dropped reads as unanswered. "Saved" clears once the next result is started. One group opens at a time (`<details name>`). The service refuses results for the Diagnostics page's entries until that page has a checklist (`VERIFY_LOCATIONS`, shared with the UI).
- **Open for Bob** (the code's choice in brackets): a result can be recorded with no tower connected (the person's word is enough); results never expire on a library or app upgrade (the newest stands, with its versions shown); a result on the mock never makes anything `mock-tested` (only tests do); devices are named by their `hello` label, so two iPads look alike.

**Bob's Verify pass, in chunks.** Run the service on the real tower (`pnpm build && pnpm start`), turn Verify mode on, and do one group at a time; each result is saved as it is recorded, so stop whenever a group ends. A suggested order, each a short sitting:

| Chunk | Page, group | Needs |
|---|---|---|
| 1 | Dashboard, Connection | Connect, Disconnect, Reconnect |
| 2 | Dashboard, Calibration | Connected tower |
| 3 | Lights, Lights | Connected; the rotation sequences need calibration |
| 4 | Sounds, Sounds | Connected |
| 5 | Mechanics, Mechanics | Calibrated; random rotate turns the lights off |
| 6 | Tower State, Seals and Skulls | Connected for Break a seal and the tower counter |
| 7 | Tower State, Glyphs, Battery and Tower state | Calibrated for glyphs |

Record a `partial` or `fail` with what was seen; Claude writes the gap entries from the notes. A `confirmed` the tower did not earn goes to the bugfix skill (GAP-LIB-010).

## Risks

- `lights` payload shape is complex. Start with the form generator for flat params and give lights a dedicated component.
- Random rotate and seal break have physical side effects. Each needs a confirmation dialog, and the reviewer checks this.
- Glyph positions are library-derived from rotation commands and may drift from reality. Label them `library-derived`, and stale after disconnect.
