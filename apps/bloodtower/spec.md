R1 is the thin foundation. It loads a story pack, shows a display-only Story board, lets devices join and press, and writes timing marks. It plays no story beyond the loaded pack's moment list. The tower is connection only: no cue is sent. The socket hub publishes one session to the board and the devices.

## 1a. Engine core decisions (accepted 2026-10-23, not yet built)

Bob ruled these in the architecture review on 2026-10-23, from the game design's loop stack (DEC-132, MEC-032 to MEC-039) and event log (DEC-107). The plan [plans/C1-engine-core.md](plans/C1-engine-core.md) builds them. Until a row's step lands, the R1 rows it replaces still describe the code. Each step updates this spec in its own commit, moves the replaced rows' text to "Replaced by D3x", and adds its traceability rows. The first sentence of each row is Bob's ruling. The rest is the shape Claude proposed in the same review, approved with this spec.

| # | Decision | Replaces | Reason |
|---|---|---|---|
| D32 | **The engine core is an event-sourced reducer.** One pure function takes the state and an event, and returns the new state and a list of effects: `(state, event) → { state, effects }`. The state is the loop stack (session → game → chapter → day → group turn → encounter → quest or battle, DEC-132), one frame per running level, each written against the loop template (DEC-143): Enter, Start point, Body, Exit (checked after a pass, DEC-137), Close, Result up, End point. Every input is an event: a press, a claim, a device joining or dropping, a tower result, a timer the host fires. Effects are what the host does: send views, run a tower command, start a timer, write a checkpoint. The core does no I/O, reads no clock and draws randomness only from `@dark-tower/rng` (decision 0005). Events are applied one at a time on the host, so the first press on a prompt wins because it arrives first, and a later press on the same prompt finds it closed and is logged as `winner: false`, not as an error. **Traceability (C1 step 3):** `bloodtower-engine` (`apps/bloodtower/src/engine`) exports `step`, versioned event and effect Zod schemas, and `advanceLoops` / `startRootLoop` for loop definitions; `pnpm check` enforces the engine import and purity rules in `scripts/check-imports.mjs`. | D20, D30's flow order, the beat list in `session/beats.ts` | Bob, 2026-10-23. The loop stack nests and repeats, and a flat screen list and a linear beat list cannot hold it. One mechanism gives Save and quit (DEC-155), stats from the log (DEC-107), exact replays and the simulator. |
| D33 | **New core, port the shell.** The core is a new part, `apps/bloodtower/src/engine` (package `bloodtower-engine`), with no `ws`, SQLite, Node or React import. The working shell flow moves onto it as the session loop's Enter and the game loop's setup: Pick Story, Game settings, Connect Tower, Claim Heroes and the pack's setup steps. `src/server/session/engine.ts` and its tests are deleted in the step that switches the host over, once the e2e suite passes on the new core. The hub, join and QR, the pack loader and lint, and the board and iPad screens stay, adapted to D36. A headless simulator command plays N seeded games from the core with scripted presses and reports their numbers. | `session/engine.ts` | Bob, 2026-10-23. Refactoring the closure in place would pull the new design back toward the old one. The prototypes' rules are not lifted: they were built for one-page tuning. Rules are written from the cards and each prototype's FINDINGS.md. |
| D34 | **Story packs are data only.** A pack is YAML or JSON plus assets. It never carries code. A story entry point (DEC-138, DEC-140) lists effects from a fixed engine set: narrate (with a tower cue), place or remove a story token, open a lead, set or clear a story flag, add to a story counter. That is the whole of what DEC-139 allows. Conditions are checks on flags, counters, the chapter and the day. Quests choose an engine quest type (the dungeon types, MEC-026 to MEC-031) and fill it. Engine content that every story shares (the hero pool, classes and virtues, building types, foes, events, quest types) is a base content pack in the same format, which a story may swap or extend where DEC-150 allows. The pack lint can then prove more of a story, for example that every chapter's quests can be reached. | R-ENG-4 (rule modules), the R1 pack schema's moment and set-piece sections | Bob, 2026-10-23. A rule a story needs that the engine lacks becomes an engine change with a card, not pack code. |
| D35 | **The host owns the tower radio through `@dark-tower/tower`** (decision 0004). The host makes one tower session from the package in its own process. The core emits tower commands only as `command{capabilityId, params}` effects. The host runs each through the package's executor and feeds the outcome back as an event (`confirmed`, `indeterminate`, `failed`, or no answer). **Replay never re-sends a tower command.** It reads the logged outcome instead, so loading a save never fires the tower. A tower cue during play runs because a person's press moved the game on, so it is not an automatic physical action. A cue that fails or gets no answer is an error: it is logged, toasted on the Story board (decision 0003), and pauses the game as a lost tower does (DEC-155). Nothing retries it. There is no play without the tower (DEC-155): the pack `tower` field and "Play without tower" go away. | D2, D10, D27's `tower` field, D30's `optional` and `none` paths | Bob, 2026-10-23. The game needs the tower, and tower-poc is an Experiment-tier app. |
| D36 | **Protocol v2: projected views and offered actions.** `PROTOCOL_VERSION` becomes 2. The host projects the core's state into one view per audience: the board view (public, the running loop levels and what each shows) and one view per iPad (its heroes, their private lines, and the actions offered to it). Each offered action has a prompt id, an action id, a label, and whether it is open or why not. iPads send one message, `act{promptId, actionId, args}`, so a new building action or quest step needs no new message type (DEC-204: every pick is an action). The board still sends nothing but `keeper-line-ended`'s v2 equivalent, a `narration-ended` report that the host acts on only for the line now showing (D7's rule, kept), and `log` (D39). Strict schemas, the private-content refusals on the board view (§3) and the no-raw-bytes rule all carry over. ## 4. Pack schema

`pack.ts` is the assembled pack (the loader in step 3 reads YAML or JSON files and hands one object here). It interprets metadata (§1), hunters and cast (§2), nights (§3.1), set pieces (§3.3), moments and targets (§4), cues (§6), asset manifest entries (§13) and stats/timing hooks (§14).

Rules the schema enforces, with the id in the issue message (`packIssues` maps an untagged Zod failure to V-1, and a missing cue `screen` or `fallback_sfx` to V-8):

| Rule | What fails |
|---|---|
| V-1 | A required field missing, an unknown key, a duplicate id, players min above max, an empty ambient map, a still or clip with no asset. |
| V-2 | An asset id that is a path; a missing manifest id; a set-piece or night ref that is not declared; a cue named by a moment that is not in the pack; a speaker who is not a hunter or a cast member. Item refs, `phase_moments`, and a phase `on_event` are not resolved in R1. |
| V-3 | A moment id outside the §4.1 grammar, or a scene prefix that is not a set piece id and not the reserved `crypt` or `end` prefix. A set piece named `crypt` or `end`. `scene.private.hunter` is not valid: the moment part is required, as in `scene.02.private.hunter`. `end.lit.01` and `crypt.wet-steps` are valid ids. |
| V-4 | `.private.<hunter>` whose hunter is not declared, or whose target is not `ipad:<hunter>`. A shared moment targeted at one hunter. A private asset whose manifest target is `storyboard`. |
| V-5 | A `~no-<hunter>` variant whose hunter is not declared. A missing variant is not a load error. Which variant plays is step 5, not the schema. |
| V-8 | A story cue whose `drums` is not `none`, unless `base_game` is true. Screen and fallback are required asset ids. `hold_s`, when present, is a positive number of seconds. R1 stores it and does not wait on it. |
| V-20 | The word `random`, or a `seed(...)` call that does not name a table id. The kingdom value `seed` is the format's seeded-order keyword and is allowed. |

`stats.timing.marks` is the literal `auto`. A pack does not author timing rows.

The loader adds folder rules on top of the schema (same `V-1` id in issues). A pack folder holds `pack.yaml` or split YAML/JSON stems, optional markdown notes (`README.md`, `CONVERSION-NOTES.md`, any other `*.md`), and optionally exactly one subfolder `assets/`. That folder holds only image files (`.png`, `.jpg`, `.jpeg`, `.webp`) with no nested folders. Any other top-level entry is refused. Markdown is never parsed as pack data. A `playable: false` pack is validated from its manifest only; sibling files are not read. A missing portrait is a `W-asset` warning. A `placeholder` still, clip, or audio asset with no file yet is a `W-asset` warning, and the pack still loads. A non-placeholder still, clip, line, music, ambient, sfx, or cover whose file is not in the pack fails the load (`V-2`).

### 4.1 Pack format v2 (D34, D38)

The host reads `packsDir` (default `packs/`). Each v2 manifest carries `format: 2` and `kind: story` or `kind: base-content`. Schemas and lint live in `src/protocols/pack-v2/`; the v2 loader is `src/server/pack/v2/`. It skips `*.md` notes and, when `playable` is false, reads the manifest alone. A non-placeholder still, clip, or audio asset whose file is missing fails (`P2-2`); a placeholder with no file yet warns (`W-asset`). `pnpm --dir apps/bloodtower pack:lint` with no argument checks `packs/test` only. `pnpm --dir apps/bloodtower pack:lint:all` lints every immediate child of `packsDir` (`.wt.json`, then `PACKS_DIR`) and, when `packs-v2/` is a separate tree, that folder the same way. `pnpm check` and `pnpm build` run `pack:lint:all` and fail when any door fails. The rules are the loader's (schema, `V-*` / `P2-*`, and `W-*` warnings). Authoring limits are `research/game-design/story-pack-format.md`.

**Story packs** carry identity, settings, `day.move_roll`, a `start` block (AREA-077 uses `one-per-kingdom-citadel`), optional game entry points, and `chapters` with kingdoms, timed beats, quests (`quest_type` names a base quest type), and entry points as lists of effects from the fixed set: `narrate` (optional tower `cue`), `place-token`, `remove-token`, `open-lead`, `set-flag`, `clear-flag`, `add-counter`. Conditions check flags, counters, chapter, day, or kingdom, combined with `and` / `or` / `not`.

**Base content packs** hold the shared hero pool (DEC-099, DEC-100), building types, quest type names, and the RtDT board graph (DEC-221): kingdoms with direction-letter ids (DEC-226), printed space names (DEC-225), terrains, optional buildings, adjacency, and river crossings. The base pack's board (`packs/base/board/spaces.json`) is generated by the board map entry tool (`apps/board-map-tool`, `pnpm export-pack`; DEC-240): each space has `neighbours` with tower-relative compass slots (DEC-234 to DEC-236), `tower_adjacent`, and a `region` that points at a `region_labels` entry with a REG- id (DEC-242, DEC-243). A story names its `base_pack` id; lint loads that folder beside the story under `packsDir`.

| Rule | What fails |
|---|---|
| P2-1 | An unknown manifest key or value, a duplicate id, or a structural mismatch (semver, kingdom letter on a space id, four kingdoms). |
| P2-2 | A ref to an undeclared space, hero, or base pack, or a non-placeholder still, clip, or audio file that is not on disk. |
| P2-3 | A flag read in a condition that is never set or cleared in the same story. |

The v2 lint refuses code in a pack: strict objects only, and effects must be one of the kinds above. A manifest without `format: 2` (the metadata-only Count) still uses the R1 rules V-1–V-20.

## 6. Tower safety

Copied here so the app spec states them. The host wires the port from step 6. A winning press is the only call.

- The Story board and the devices do not talk to the tower. The Mac host will, as a client of tower-poc. Outbound messages are `hello`, `connect` and `calibrate` only (D10). It does not send `command`.
- No bloodtower message carries raw bytes.
- Nothing physical happens automatically: no auto-calibrate, no auto-reconnect, no automatic retry.
- Mechanics that need calibration stay unavailable until a person calibrates. R1 does not offer mechanics.
- Unknown tower values are `unavailable`, never zero.
- R1 sends no light, sound, drum, seal or skull command. `DIAG_LOG` is for a later hardware session.
