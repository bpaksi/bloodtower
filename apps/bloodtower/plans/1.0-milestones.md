## Unblocking

Read from the cards on `main` (`fcdb2490`), 2026-10-31.

**Design questions are no longer the bottleneck.** Every question on punch list part B is answered or parked, the battle set and the finale included. Only three 1.0 questions are open:

| Question | Blocks | How it gets answered |
|---|---|---|
| Q-402: the drums and trapped skulls on Continue | C2 feature 11 | Bob runs C2 feature 10 on the real tower, then rules |
| Q-401: what to change in Pick story | C2 feature 14 | Bob says what is wrong with the carousel |
| Q-396: can a plain scene's hit-point cost fell a hero? | C3's plain scenes | One answer from Bob |

**What does block the work:**

1. **Approvals.** Nothing is built until Bob approves a feature's evals and mockup. C2's first ten folders are ready for that now.
2. **C2's session shell is serial.** Features 05 to 08 all rework `engine/loops/session`, so they go one at a time.
3. **C3 is not planned yet.** Its engine work is in other folders (`engine/loops/{chapter,day,group-turn,encounter}`, new loop levels, `packs/`, pack v2 loading), so it can build in parallel with C2's serial shell. C3 does not have to wait for G-C2. Only its screens wait, because they sit in the shell.
4. **66 mechanics have no screen, UI piece or cue** (`pnpm graph gaps`). About half are pack toolkit tools (MEC-040 to MEC-070), which a pack builds and no screen needs. The gameplay ones (events, buildings, battle, the quest types, the Tower) need their screens named before their UI can be planned. Their engine work can be planned and built first.
5. **Two reviews wait on Bob.** The corruption rulings DEC-466 to DEC-477 are still "Claude for Bob" (punch list B11). The old-doc conflicts are 49 `conflicts` links on 30 cards (B12); a developer could read the wrong document.

**The order that frees the most work:**

1. Bob approves the C2 folders. Six features can then build at once (C2 batch B1), and feature 10 puts the tower run in Bob's hands.
2. Claude writes the C3 plan and its engine feature folders now, against the audit's C3 lines. Those features run beside C2's 05 to 08.
3. A design session gives the gameplay mechanics their screens: the ones from item 4 that are not pack tools. That unblocks C3's UI features and the C4 plan.
4. Bob answers Q-396, reviews DEC-466 to DEC-477, and runs feature 10 on the tower (Q-402).
5. Claude writes C4 once C3's loops have landed, and C5 once A1's asset adapter is planned.

## Rules across the four

- **Each step builds 1.0 cards only.** A step lists the deliverables it builds as `Builds:` (DEC-355, DEC-505), and only 1.0 deliverables (DEC-696). A step that writes a pack lists its story's area, AREA-097 for The Ruined Keep, instead of each story card (DEC-697).
- **The 1.0 gap list is shared out.** DEC-696 makes the 1.0 list of `pnpm graph gaps` the to-do list. Each milestone plan names the gaps it closes. G-1.0 needs the list empty.
- **Claude plans; builders build.** Claude writes each plan and its feature folders, and Bob approves each feature's evals. Wright's developers build them (C2 plan, "Who does what").
- **Dracula is not in 1.0.** It ships in a drop after 1.0 (DEC-691). The only Dracula change in these plans is C2 feature 01, which takes Long out of its settings (DEC-502, DEC-508).
- **Tower safety and the error rule hold in every step**, as in the root `CLAUDE.md`.
